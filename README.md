# Backend (NestJS + Prisma + PostgreSQL)

Бэкенд поверх PostgreSQL в Docker: модуль каталога (категории и товары, уже
подключён к витрине) и модуль заказов (оформление корзины). Данные каталога —
те же тестовые товары, что раньше лежали в `storefront/lib/mock-data.ts`.

## Запуск с нуля

1. Поднять базу данных (Docker Desktop должен быть запущен):

   ```
   docker compose up -d
   ```

   Поднимутся два контейнера: `storefront-db` (PostgreSQL на порту 5432) и
   `storefront-adminer` — веб-интерфейс для просмотра таблиц на
   http://localhost:8080 (система: PostgreSQL, сервер: `db`, пользователь:
   `storefront`, пароль: `storefront`, база: `storefront`).

2. Установить зависимости:

   ```
   npm install
   ```

3. Накатить схему БД:

   ```
   npm run prisma:migrate
   ```

   При первом запуске (таблицы `categories`/`products`) попросит имя миграции —
   можно ввести `init`. При появлении новых таблиц (`orders`, `order_items`,
   `users`) команда создаст ещё одну миграцию — имя можно дать по смыслу
   (например, `orders`, `users`).

4. В `.env` задать `JWT_SECRET` (случайная строка — см. комментарий в
   `.env.example`, там же команда для генерации) и, если нужен сразу готовый
   вход в админку, `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`.

5. Наполнить БД тестовыми данными каталога (и создать/обновить администратора
   из `.env`, если заданы `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`):

   ```
   npm run seed
   ```

6. Запустить сам бэкенд:

   ```
   npm run start:dev
   ```

   После старта в консоли появится `API запущен: http://localhost:3001/api/v1`.

## Проверка

Каталог — откройте в браузере:

- http://localhost:3001/api/v1/catalog/categories — список категорий
- http://localhost:3001/api/v1/catalog/products — список товаров
- http://localhost:3001/api/v1/catalog/products/display-iphone-13 — карточка товара

Если видите JSON с данными — бэкенд и база работают.

Заказы проверяются через оформление заказа на витрине (`/checkout`) — после
успешного оформления открывается страница `/order/<id>`, а сам заказ можно
посмотреть в Prisma Studio (`npm run prisma:studio`, таблица `orders`) или в
Adminer.

## Управление каталогом

Категории и товары добавляются и редактируются через собственную админку на
фронте (`/admin` — вход по email/паролю сотрудника, см. ниже). Prisma
Studio/Adminer остаются как техническая возможность (например, разово
поправить что-то напрямую в БД), но для повседневной работы не нужны.

## Пользователи и вход (`src/auth`, `src/users`)

- `POST /auth/register` — регистрация покупателя: email ИЛИ телефон (хотя бы
  один) + пароль, без подтверждения письмом/смс (сознательное упрощение).
- `POST /auth/login` — вход по `emailOrPhone` + `password`, отдаёт `{ user, token }`.
- Токен — обычный JWT (подписывается `JWT_SECRET`, живёт 30 дней), передаётся
  как `Authorization: Bearer <token>`. Пока без refresh-токенов — по истечении
  30 дней нужно просто войти заново.
- `GET/PATCH /users/me`, `GET /users/me/orders` — профиль и история заказов
  покупателя (требуют токен).
- Роли: `customer` (по умолчанию), `manager`, `admin` — первому админу роль
  выставляет `npm run seed` (см. `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` в
  `.env`), остальным сотрудникам роль пока меняется вручную в БД (Prisma
  Studio/Adminer) — отдельного UI для управления пользователями ещё нет.
- Эндпоинты `/admin/**` защищены и токеном (нужно быть залогиненным), и ролью
  (`admin` или `manager`) — см. `JwtAuthGuard`/`RolesGuard`/`@Roles()` в
  `src/auth`. Заказ (`POST /orders`) по-прежнему можно оформить и без входа
  (гостевой чекаут) — токен там не обязателен, но если он есть и валиден,
  заказ привяжется к аккаунту для истории покупок.

## Поиск и фильтры по каталогу (`src/catalog`)

- `GET /catalog/products` — тот же эндпоинт, что и раньше, но теперь принимает
  необязательные `category`, `q` (поисковая строка), `compatibility`
  (slug'и моделей устройств через запятую, см. ниже), `minPrice`/`maxPrice`,
  `sort` (`new` по умолчанию, либо `price_asc`/`price_desc`).
- Поиск по `q` — полнотекстовый, средствами PostgreSQL
  (`to_tsvector`/`plainto_tsquery` с русской конфигурацией + `ts_rank_cd` для
  сортировки по релевантности), считается на лету по названию, описанию и
  тексту совместимости — без отдельного индекса. Если каталог заметно
  вырастет (тысячи товаров), стоит завести generated tsvector-колонку с
  GIN-индексом — пока для этого нет необходимости.
- `GET /catalog/compatibility?category=<slug>` — список моделей устройств
  (`CompatibilityModel`), сгруппированный по производителю, для чекбоксов
  фильтра; без `category` — по всему каталогу (страница `/search` на фронте).
  Отдаёт только модели, у которых реально есть хотя бы один товар.
- Модель устройства и товар связаны явной таблицей `ProductCompatibility`
  (многие-ко-многим) — не путать с `Product.compatibility` (это просто текст
  для отображения на карточке, как и раньше). Управляется через форму товара
  в админке (чекбоксы моделей) — `POST/PATCH /admin/catalog/products`
  принимают `compatibilityModelSlugs`.
- Это отдельная миграция БД — если база уже была развёрнута раньше, один раз
  выполните `npm run prisma:migrate`, а затем `npm run seed`, чтобы
  протестировать фильтры на тестовых данных (иначе `CompatibilityModel` и
  связи будут пустыми, а поиск по тексту продолжит работать и без них).

## Артикул и наличие товара (`Product.article`, `Product.inStock`)

- `article` — необязательный уникальный текстовый код товара (например,
  `BAT-001`). Задаётся вручную в форме товара в админке, участвует в
  полнотекстовом поиске (`GET /catalog/products?q=`) наравне с названием и
  описанием. Схема кодов в `prisma/seed.ts` условная (не привязана к
  реальному прайс-листу поставщика) — просто пример для тестовых данных.
- `inStock` — булево поле, по умолчанию `true`. Переключается чекбоксом в
  форме товара, на витрине показывается как бейдж «Под заказ» (когда `false`)
  на карточке товара и в каталоге, никак не влияет на фильтры/поиск. Сейчас
  это чисто ручной флаг: реальной синхронизации со складом, 1С или другой
  учётной системой нет — если она появится, значение этого поля нужно будет
  обновлять оттуда (например, отдельным импортом или вебхуком).
- Это отдельная миграция — если база уже была развёрнута раньше, один раз
  выполните `npm run prisma:migrate`, затем `npm run seed` (тестовым товарам
  проставятся артикулы и пара из них станет «под заказ» для проверки бейджа).

## Отчёты для бухгалтерии (`src/admin`)

Раздел «Отчёты» в админке (`/admin/reports`) — сводка по выручке/заказам за
период и реестр заказов, каждый доступен и как таблица в браузере, и как
скачиваемый `.xlsx` (собирается на бэкенде через `exceljs`, новую зависимость
нужно поставить через `npm install`, если делаете `git pull` на уже
развёрнутом бэкенде).

- `GET /admin/reports/summary?from=&to=&groupBy=day|week|month` — выручка и
  количество заказов по периодам (день/неделя/месяц), отдельно отменённые
  заказы (`cancelledCount`/`cancelledAmount`) и итоговая строка. Без `from`/`to`
  — по умолчанию текущий календарный месяц.
- `GET /admin/reports/summary.xlsx` — тот же отчёт как файл Excel (те же
  параметры `from`/`to`/`groupBy`).
- `GET /admin/reports/orders?from=&to=&status=` — реестр заказов за период
  (тот же список, что видит `/admin/orders`, но с фильтром по датам и
  опционально по статусу).
- `GET /admin/reports/orders.xlsx` — реестр заказов как файл Excel.
- **Важная оговорка**: у магазина пока нет ни онлайн-оплаты, ни фискализации
  (см. `src/orders` — заказ создаётся как заявка, статус меняет менеджер
  вручную). «Выручка» в отчётах — это сумма по всем заказам за период, кроме
  отменённых (`new` + `confirmed` + `done`), т.е. ориентировочная сумма продаж
  по заявкам, а не подтверждённое поступление денег. Для реальной бухгалтерии
  эти цифры нужно сверять с фактическими оплатами — отчёт задуман как
  вспомогательная выгрузка, а не как замена бухучёта.

## Структура

- `prisma/schema.prisma` — схема БД: пользователи (`User`), категории, товары,
  модели устройств для фильтра совместимости (`CompatibilityModel` +
  `ProductCompatibility`), заказы (`Order`/`OrderItem`).
- `prisma/seed.ts` — тестовые данные каталога (включая модели устройств и
  связи с товарами) + создание/обновление администратора из `.env`.
- `src/auth` — регистрация, вход, JWT-гвард, гвард по ролям.
- `src/users` — профиль и заказы текущего пользователя (`/users/me/**`).
- `src/catalog` — модуль каталога: контроллер + сервис (запросы к БД через Prisma).
- `src/orders` — модуль заказов: `POST /orders` (оформление, гость или
  залогиненный), `GET /orders/:id` (просмотр одного заказа — для страницы
  подтверждения на витрине). Полный список заказов — под `/admin/orders`
  (роли admin/manager) и `/users/me/orders` (свои же заказы). Оплата и расчёт
  доставки — заглушки (нет подключённых аккаунтов ЮKassa/СДЭК): заказ
  создаётся со статусом `new`, дальше менеджер связывается с покупателем вручную.
- `src/admin` — CRUD каталога, управление заказами и отчёты для бухгалтерии
  (сводка + реестр заказов, JSON и `.xlsx` через `exceljs`) для собственной
  админки на фронте, защищено `JwtAuthGuard` + `RolesGuard` (роли admin/manager).
- `src/prisma` — обёртка над Prisma Client как сервис Nest (подключение/отключение от БД).
- `docker-compose.yml` — PostgreSQL + Adminer для локальной разработки.
